Re.从零开始的飞行器生活：通信与遥控系统详解

2026-09-06 drone

在上一期控制与导航系统中，我们已经把飞控、传感器、SLAM 和机载计算机的分工拆开讨论过了。但即使飞机已经能稳定悬停，它仍然需要面对几个很实际的问题：操作者怎样接管控制它？地面站怎样看到它的飞行状态、任务情况和定位坐标？小车发现目标后怎样通知飞机？机载相机的画面怎样低延迟地回到地面？

这些问题共同构成了本节的主题：通信与遥控系统。

对电赛而言，通信并不是简单的加一个无线模块就结束的工作。它既服务于调试，也可能是任务链路的一部分；既要传少量但不能丢的控制信息，也可能要传大量且允许偶尔丢帧的视频（也可能有需要传输大量数据且不能丢失关键数据帧的情况）。不同信息对延迟、带宽、可靠性和失效后果的要求完全不同，不能用同一条链路、同一种协议简单解决。

历届电赛出现过四旋翼自主飞行器、多旋翼自主飞行器、四旋翼探测跟踪、植保飞行器、空地协同智能消防系统、立体货架盘点无人机等任务。它们的共同点是：飞行控制必须独立可靠，而无线通信负责操控、观测、协同和任务信息交换。具体比赛是否允许遥控干预、图像回传、局域网或机—车通信，必须以当年题目和器件清单为准，不能照搬往届方案。

1. 先把“通信”拆成几条不同的链路

一架参加电赛的飞行器，常见的无线链路至少有下面几类：

  • 遥控链路：操作者 → 遥控接收机 → 飞控，用于解锁、模式切换、手动操纵和紧急接管；
  • 数传链路：飞控经机载计算机 ↔ 地面站，用于状态回传、参数配置、日志和调试；
  • 图传链路：机载相机 → 显示端或地面站，用于观察画面、目标确认和视觉算法调试；
  • 任务协同链路：飞机 ↔ 小车，或飞机/小车 ↔ 地面站，用于交换任务状态、目标信息和协同指令；
  • 机内通信：飞控 ↔ 树莓派/地瓜派/雷达/相机，通常是串口、USB、以太网、CAN、I2C 或 SPI，不应和无线空口混为一谈。

在当前系统中，应把机载计算机作为任务网络的中心：任务代码、飞机—小车协议、视频服务和地面站网络接口都运行在它上面。接收机只把遥控通道送给飞控；它既不转发任务数据，也不参与飞机与小车之间的业务通信。

可以把一个较完整的空地协同系统理解为：

机载电脑可将飞控遥测转发给地面站，也可将经过任务逻辑检查后的目标经机内链路发送给飞控；这不改变其权限边界：飞控只接受经过定义的控制输入和任务目标，接收机只服务于遥控与安全接管。地面站负责显示、配置和人工决策，小车只接收完成自身任务所需的信息。不要让地面站、树莓派和小车同时给飞控发送“电机油门”。

2. 遥控器与接收机：最重要的安全接管链路

遥控器把摇杆、开关和旋钮转换为无线控制帧；接收机收到后，将各通道信息送入飞控。典型通道包括：

  • 油门、横滚、俯仰、偏航四个基础操纵量；
  • 解锁/上锁开关；
  • 飞行模式切换，例如手动、定高、定点或外部控制；
  • 紧急降落、返航或任务启停等安全开关。

遥控器和接收机之间常工作在 2.4 GHz 频段，也有面向更远距离的其他频段方案。现代接收机通常会采用跳频、纠错、双向遥测等机制；接收机与飞控之间则常使用 PWM、PPM、SBUS、IBUS 或 CRSF 等接口。对新系统而言，串行数字接口能减少多根 PWM 线，并能提供更多通道或链路质量信息，但是否兼容仍必须查看飞控与接收机的说明书。

遥控链路的核心指标不是吞吐量，而是可预测的低延迟和失联可判定性。飞控应持续检查控制帧是否按预期到达，而不是只看“接收机是否曾经连上”。一旦超过超时门限，应按已验证的策略进入悬停、降落、返航或上锁；室内无可靠定位时，盲目返航并不安全，通常应选择受控降落或保持姿态后降落。

在电赛自主任务中，遥控器经常只用于赛前解锁、模式预置和紧急接管。一般明确要求飞行过程中不得人为遥控干预。这不意味着遥控系统不重要，恰恰意味着需要在开赛前把模式、失联保护和安全接管逻辑验证清楚。

2.1 接收机安装并不是小事

接收机应远离电调、大电流电源线和降压模块，天线不能被碳板、电池或金属完全遮挡。两根分集天线应尽量保持不同朝向，不要并排捆在一起；同轴馈线不能被锐角折弯或被螺旋桨扫到。

完成安装后，至少应做三项测试：断开发射机验证 failsafe；让电机逐步升高油门时观察 RSSI/链路质量是否恶化；在比赛场地边界和不同机头朝向下检查是否有明显死角。只有“桌上能收到”并不能说明飞行时可靠。

现在使用的富斯遥控器和接收机只要供电没问题，一般信号都很好。测评前一定要确认好导线连接是否正常。

3. 数传与地面站：传状态和任务，不直接取代飞控

在本系统中，数传应由机载计算机统一管理：飞控先通过机内串口、USB 或以太网把 MAVLink 等状态送到机载计算机，再由机载计算机经 Wi-Fi 热点或专用数传转发给地面站。这样任务程序可以同时读取飞控状态、执行任务状态机并控制数据流，接收机始终只承担 RC 通道。

以 PX4 等开放飞控为例，常见上层协议是 MAVLink：飞控可向机载计算机发送姿态、位置、电量、飞行模式、定位质量和故障告警；机载计算机再按需要向地面站发布这些信息。地面站的任务授权、参数配置或航点请求也应先由机载计算机接收、校验，再通过机内链路交给飞控，而不是通过接收机转发。

数传模块可能是成对的透明串口电台，也可能通过 Wi-Fi、以太网或 USB 网络承载协议。无论底层使用什么模块，应用层都应明确区分：

  • 高频、短小、必须及时处理的心跳和安全状态；
  • 中频的姿态、电量、位置和链路质量；
  • 低频或可延后的参数、日志、地图和文件传输；
  • 只在确认条件满足后才执行的任务指令。

（调试）地面站的价值首先是“看见系统”，而不是在飞行中频繁改参数。比赛现场最实用的界面通常只需要显示飞行模式、解锁状态、电池电压、定位质量、外部控制心跳、通信质量和关键任务阶段。把几十个调参页全部打开，反而更容易在紧张时漏掉真正的故障告警。

如果机载计算机在 Offboard 模式下向飞控持续发送速度、位置或轨迹目标，应由飞控检查更新频率和超时。数传中断、地面站退出或机载程序卡死时，飞控不能继续执行最后一条旧指令。飞控的姿态稳定、限幅和失效保护必须不依赖地面站在线。

4. Wi-Fi：适合大带宽局域网，但要管理好角色

Wi-Fi 的优势是吞吐量高、可直接连接手机、电脑、树莓派和网络摄像头，特别适合室内赛场的图像回传、远程终端、ROS 消息、网页控制台和调试日志。当前架构可由机载计算机建立热点，地面站和小车作为客户端加入；任务代码在机载计算机上监听和发送 Wi-Fi 消息。这能让任务网络随飞机移动，且不依赖接收机提供数据通道。

但 Wi-Fi 不是天然的“可靠控制链路”。2.4 GHz 频段常同时被遥控、蓝牙和周围热点占用；自动选信道、漫游、省电休眠、拥塞重传和视频突发流量都会造成延迟抖动。因此建议：

  • 为比赛系统固定网络角色，例如由机载计算机做 AP，地面站和小车做客户端；若使用专用路由器，也应明确它与机载计算机的网关关系（比赛不一定允许在场地搭建无线局域网）；
  • 预先固定信道、SSID、密码和 IP 规划，关闭无关设备的自动连接；
  • 将控制/状态和视频分端口、分进程；
  • 给任务消息加序号、时间戳、确认和超时，而不是相信 TCP 连接存在就代表对方仍在正常工作。

机载计算机通过 Wi-Fi 向地面站发送图像时，常见误区是把高码率视频与控制消息塞在同一条不加限制的队列里。网络拥塞后，过期视频帧和过期控制指令会排队到达，看到的画面“没断”，实际延迟却已不可用。实时视频更关注最新帧，应该允许丢弃积压帧；任务控制更关注消息是否被正确、及时地处理，应使用独立的节流和确认机制。

5. 蓝牙：适合近距离配置与少量协同信息

蓝牙的优点是手机和低功耗 MCU 支持广泛、配对方便、开发门槛低。若选择蓝牙作为飞机—小车链路，应把蓝牙模块接在机载计算机一侧（USB、UART 或板载蓝牙），由任务代码收发协议帧；不能把它接到接收机上再期待接收机转发任务数据。经典蓝牙串口模块可以把无线链路近似当作串口；BLE 则更适合周期性状态上报、配置页面和低功耗传感器。对于电赛，蓝牙很适合：

  • 在调试阶段用手机或电脑配置小车任务参数；
  • 在近距离发送“开始/暂停/完成/故障”等少量状态；
  • 调试阶段读取传感器数值或查看日志；
  • 作为飞机与小车之间的备份状态通道。

它不适合作为高速图传，也不宜作为唯一的飞控控制或紧急保护通道。蓝牙同样占用 2.4 GHz，人与设备遮挡和多设备配对都会影响表现。若飞机和小车都使用蓝牙，应在程序中限定连接对象、重连次数和超时，并避免让手机临时接入后改变系统拓扑。

一个朴素但可靠的做法是：蓝牙只传结构化短帧，例如 队列号、消息类型、负载长度、数据、校验，而不是传可读但难以验证的任意文本。小车收到“开始灭火”或“目标已发现”后应回复确认；发送方在规定时间未收到确认时，只能重发有限次数并上报告警，不能无限阻塞等待。

6. 图传：先区分“给人看”与“给算法用”

图传传输的是视频或图像，数据量远高于遥控与数传。它常见于两种目的：

  • 操作者观察现场、确认任务和辅助接管；
  • 机载视觉算法把识别结果、关键帧或调试画面交给地面站。

模拟图传通常端到端延迟低、链路衰落时表现为雪花或画质下降；数字图传画质更好，能提供编码、纠错和网络化接入，但会有编码缓存、重传和解码带来的延迟，信号不足时也可能突然卡顿。无论哪一种，图传都不应成为姿态闭环的必经环节：飞机的姿态控制和基本避障不能依赖“地面端看见一帧画面后再发指令”。

对电赛室内任务，往往没有必要回传完整高清原始视频。若目标识别已经在机载完成，优先回传目标类别、坐标、置信度、缩略图和任务状态；需要人工确认时再降低分辨率或帧率，换取更低延迟和更稳定的链路。这样能显著降低 Wi-Fi 对数传的挤占。

图传调试应记录端到端延迟，而不只看“帧率”。可以在画面中显示机载单调时钟或 LED 闪烁，再与地面显示时间比较；同时分别记录采集、编码、发送、接收和显示时间，才能知道延迟究竟来自相机、编码器还是网络。

往年飞行器组还没有考过图传的相关内容，但2026年H题出现了图传任务，我们需要做好相关技术研究和调试。

7. 飞机、小车与地面站怎样分工通信

空地协同任务最容易犯的错误，是把“谁能无线发消息”误当成“谁应该决策”。更稳妥的职责划分如下：

节点 主要职责 典型上行信息 典型下行信息
飞机飞控 姿态、位置和安全控制 模式、电量、故障、定位状态 解锁/模式、经过约束的任务目标
机载计算机 运行任务代码；识别、SLAM、规划、协议网关 飞控遥测、目标、轨迹状态、识别结果 任务阶段、协同目标、停止指令；经机内链路发送给飞控的受约束目标
小车控制器 行驶、执行机构和本地安全 位置、到位、障碍/故障状态 任务编号、目标点、开始/暂停
地面站 监控、记录、人工授权 全系统遥测、图像、告警 高层任务授权、人工接管

飞机和小车交换的应是“任务语义”，而不是彼此的电机量。例如小车发送 TARGET_FOUND(x, y, confidence)，飞机或地面站回复 ACK；飞机到达观察位后发送 AIRCRAFT_READY；小车确认安全区域后才进入下一阶段。每条消息应至少包含任务编号、序号和时间戳，接收端只处理当前任务且序号更新的消息，避免重连后旧包重新触发动作。

当任务要求飞机给小车指路时，也不要让小车盲目跟随网络上一次收到的坐标。小车应验证坐标系、数据时效、允许速度和自身传感器状态；超过时限仍未更新时，减速、停车或回到安全状态。飞机也一样：小车掉线不能迫使飞机悬停到电量耗尽，必须有一个与当前比赛场地相匹配的超时降级策略。

8. 电赛方案如何选：从任务反推链路

在赛题尚未明确前，最值得准备的不是某一款无线模块，而是一套可替换的分层结构：飞控保留遥控接收机和本地 failsafe；任务代码运行在机载计算机，通过串口或以太网与飞控通信；机载计算机建立热点并通过 Wi-Fi 与地面站、小车交换任务数据；蓝牙只承担近距离配置或低速备份信息；视频单独限速。

可以按下面的任务需求选择：

  • 只需要人工操纵与紧急接管：遥控器 + 接收机已经是主链路；
  • 需要看飞行状态、调参数、记录日志：增加低带宽数传与地面站；
  • 需要室内图像回传、网络调试或 ROS：使用 Wi-Fi 局域网，并保留遥控独立性；
  • 需要飞机与小车近距离交换几个状态：蓝牙或低速 Wi-Fi 都可，优先选择团队能充分测试的方案；
  • 需要稳定视频：使用独立图传，或至少对 Wi-Fi 视频进行码率和队列限制；
  • 题目禁止飞行过程中的外部干预：把无线通信降为赛前配置、状态记录或题目明确允许的功能，不能让它隐性参与控制闭环。

2013 年的四旋翼题、2015 年的多旋翼题、2017 年的探测跟踪题，以及 2023 年的空地协同题，体现了从自主飞行到感知、协同任务的演变。但这只能帮助我们准备通用能力，并不是对新题规则的替代。比赛拿到题目后，通信相关限制应当作为第一轮需求评审内容：允许哪些设备、是否允许 Wi-Fi/蓝牙、是否允许外部计算机、是否允许人工干预、是否要求视频显示，以及允许的场地范围和电磁环境。

9. 无线链路为什么会在飞机上变差

飞行器上的通信问题往往不是协议写错，而是电磁、供电和安装共同造成的：

  • 电调和电机的大电流开关会产生宽带干扰；
  • 碳纤维、金属支架、电池和人体会遮挡或改变天线方向图；
  • 降压模块纹波可能通过供电或地线进入接收机、相机和无线模块；
  • 多个 2.4 GHz 设备同时工作会产生同频竞争；
  • 机体姿态不断变化，导致极化方向和遮挡关系也在变化；
  • 振动会使 USB、天线座和排线间歇接触不良。

因此，通信设计也要回到结构和供电：天线外露并远离螺旋桨；射频线与大电流线分开布置；无线模块使用稳定、留有余量的电源；信号线有可靠共地和应力释放；机载电脑、飞控、相机和数传模块都能在电机全油门时保持不重启。不要为了解决干扰而随意把所有地线断开，正确做法是先检查供电回路、布局、接插件和滤波。

10. 失联、延迟与权限：通信系统的安全边界

每条通信链路都应写清三件事：谁有权发命令、命令多久失效、失效后设备做什么。一个可执行的原则是：

  • 遥控失联：飞控执行已测试的 RC failsafe；
  • 数传或地面站掉线：飞控继续本地稳定，不等待地面站；
  • 机载计算机掉线：飞控退出外部控制，进入预设安全模式；
  • 小车协同链路掉线：飞机和小车各自进入本地安全状态，不互相无限等待；
  • 图传中断：只影响观察能力，不能改变飞控的基础安全逻辑。

任务状态机不要只依赖一次“开始”消息。应有心跳、时间戳、超时、幂等命令和明确的 IDLE → ARMED → RUNNING → COMPLETE/ABORT 状态迁移。这里的“幂等”意味着同一条开始或停止命令重复到达时，不会造成重复起飞、重复投放或重复执行。

在所有安全动作中，飞控优先级最高。地面站只能提出请求，不能越过飞控直接驱动电机；机载计算机和小车也一样。这条边界既能防止网络抖动造成危险，也能让各模块分别测试。

11. 建议的调试顺序

不要第一次联调就让飞机、小车、图传和自主任务全部启动。更稳妥的顺序是：

  1. 桌面确认接收机通道、模式开关和 RC failsafe；此时必须拆桨。
  2. 单独验证数传：地面站能看到正确的模式、电压和链路状态，断开后不会改变飞控安全状态。
  3. 单独验证 Wi-Fi/蓝牙：检查 IP、配对、消息格式、序号、重连和超时。
  4. 单独压测图传：逐渐提高码率，观察是否影响数传、机载计算机负载和控制消息延迟。
  5. 用两台电脑或开发板模拟飞机与小车的任务状态机，故意丢包、重复包、乱序包和重启一端。
  6. 无桨或系留条件下进行整机电磁测试，再从低速、短距离、可随时接管的飞行开始。

每次测试都应记录时间、距离、机头朝向、链路质量、丢包、平均与最大延迟、电池电压、视频码率和故障现象。这样出现问题时，才能区分是射频遮挡、供电掉压、CPU 占满、协议阻塞还是飞控配置错误。

12. 常见误区

12.1 用 Wi-Fi 直接做唯一遥控

Wi-Fi 很方便，但它的时延和丢包表现通常不如专用遥控链路可预测。除非赛题明确如此要求并且完成了充分验证，否则应保留独立遥控接管与飞控 failsafe。

12.2 把图传当成数传

视频流量大、可丢帧；状态和控制消息小、必须有时效。两者应分开限速、分队列处理。图传卡顿时，不能让地面站心跳和任务停止命令也排在过期视频后面。

12.3 只看“连接成功”，不测失联

真正危险的场景是设备掉电、网线松动、程序卡死、信号遮挡和消息延迟。每一条链路都应在安全条件下主动断开测试，确认系统进入预期状态。

12.4 飞机和小车使用不同坐标系

飞机可能使用 NED 或地图坐标，小车可能用赛场平面坐标。协同信息必须包含坐标系定义、单位、原点和航向约定；不要只发送“x=2.0，y=1.0”而不说明它相对于哪里。

13. 总结

通信系统不是飞行器外面附加的一层“遥控功能”，而是把人、飞控、机载计算机、小车和地面站组织成完整系统的信息通道。遥控链路负责安全接管，数传链路负责状态和任务，图传负责观察，Wi-Fi 适合室内高带宽局域网，蓝牙适合近距离的低速配置与协同；每一种链路都应有清晰职责，不能相互越权。

面向电赛，最有价值的准备是建立能替换、能观测、能失联降级的通信架构。赛题一旦确定，再根据是否允许外部通信、是否需要空地协同、是否需要图像显示和是否禁止人工干预，删减或启用相应链路。通信模块选得再强，也不能替代飞控本地的稳定控制和安全保护。

下一篇，我们将继续介绍飞行器的任务载荷与视觉感知系统：相机、云台、激光雷达和机载计算机怎样从“采到数据”走向“识别目标、理解场地并生成任务结果”。重点会放在电赛常见的颜色/标记识别、目标定位、图像处理链路，以及载荷安装、供电、视场和计算资源如何共同影响最终表现。
